# 滑杆预览的等待时间

Vue 的基础调整和去朦胧参数都走同一套预览调度。拖动时立即开始 L2 快预览，后续输入合并最新参数，上一请求结束后等待 45 毫秒再启动下一次更新；松手后立即用最终参数请求 L2，再在 100 毫秒空闲后升级全分辨率。升级等待本代最终 L2 完成，避免迟到的低分辨率结果覆盖全分辨率。Swift 原生编辑器的空闲升级也为 100 毫秒。刷新期间保留当前可见图片。

仅效果图模式不再先请求原图。切换到原图或对比模式时按需加载对应原图；已有的原图不会因基础参数变化而重复解码。

## 为什么去朦胧算子不到一秒，预览仍要数秒

之前的算子验收从已解码的线性 RGB 数组开始，测到约 0.65–0.90 秒。全分辨率接口还包括 RAW 解码、镜头校正、基础/理光调整和 JPEG 编码；前端此前还串行请求了原图。因此算子时间不能当作从松手到显示完成的时间。

2026-10-07 用 `LCR_9472.NEF`（6064×4040）、去朦胧强度 0.85、自动模式、Python 基础调整路径实测旧完整接口：

| 阶段 | 时间 |
| --- | --- |
| 额外的原图请求 | 1.31 秒 |
| 效果图 RAW 解码 | 1.07 秒 |
| 去朦胧 | 0.78 秒 |
| 镜头校正 | 1.55 秒 |
| 基础调整 | 1.45 秒 |
| 其余转换与 JPEG 编码 | 约 0.55 秒 |
| 效果图接口合计 | 5.40 秒 |

这些数值不包含前端定时器、旧请求排队、HTTP 传输和浏览器图片解码，也不是用户当前运行实例的计时。

## 内存缓存与回收

图像缓存只放进程内存，没有磁盘图片缓存。全分辨率仅保留当前一张照片的以下层，合计不超过 640 MiB：

| 缓存 | 上限 | 复用范围 |
| --- | --- | --- |
| 只读解码图与元数据 | 256 MiB | 原图、去朦胧参数变化、效果预览及导出 |
| 去朦胧与镜头校正后的只读 RGB8 底图 | 96 MiB | 基础滑杆和理光参数变化 |
| 已校正的相机 RGB16、参考 RGB16 与白平衡 | 共享合计预算 | 相机配置、去朦胧参数变化及兼容的导出 |
| 曝光之前的增强相机 RGB16 与诊断 | 共享合计预算 | 手动曝光变化 |

换到另一张全分辨率照片或源文件变化时，先释放旧层再解码；会话淘汰时清理对应图。60 秒没有全分辨率请求后释放全部全分辨率层及配置 GPU 资源；后端退出取消回收计时器并清空。计时器是 daemon，不捕获图像数组。超过容量的图仍能渲染，但会绕过留存或淘汰部分层。

去朦胧参数、算法版本、模式、自动曝光、色彩模式或后端变化只让处理后的底图失效，同张解码图仍可复用。基础参数变化重新执行后续调整及编码。导出可借用经过文件身份验证的全分辨率源 RGB16 与相机／参考校正源图，仍重新计算增强效果，并重新读取原始 CFA 与 RAW 元数据；不使用 RGB8、JPEG 或已处理的预览效果。未命中时回到完整读取路径。

低分辨率处理、显示、去朦胧数组缓存分别有 96、64、64 MiB 上限，相机源图缓存限 128 MiB。去朦胧与理光 JPEG 缓存各限 16 MiB，同时保留 128 个条目上限。加上全分辨率合计预算，主要 NumPy/JPEG 缓存上限合计约 1024 MiB，另有数量受限的缩略图、镜头计划和少量元数据；这不是整个进程的内存上限。GPU 源图、输出缓冲与处理临时数组需要另算。

此前 2450 万像素照片的两层全分辨率缓存实际为 210 MiB，当前启用相机配置后的四层约 630 MiB。回收时先清空数组引用，再回收 Python 循环引用，并尝试 Darwin `malloc_zone_pressure_relief` / Linux `malloc_trim` 归还空闲页。符号缺失时安全跳过；Windows 尚未实测。该钩子只在空闲回收或关闭时执行。此前 macOS 实图诊断进程峰值约 2322 MiB，触发空闲回收后 RSS 约 287 MiB；这些是旧两层方案的数据，不代表当前进程或 Tauri 整个应用的内存测量。

## C++ 镜头校正

镜头畸变和色差不能用单一 3×3 矩阵表达。现在缓存 Lensfun 已初始化的镜头参数计划，最多 4 项；焦距、光圈、距离、尺寸或校准文件变化会生成新计划。坐标按 128 行生成，用 C++ CPU 从连续 RGB16 数组重采样，避免原来的每条带、每通道整图复制。完整坐标图不常驻内存。暗角仍由 Lensfun 的原生绑定处理。

保持双线性插值和 reflect101 边界，并检测本机 OpenCV 的 float-map 插值路径；优化库可能使用连续坐标，普通路径使用 1/32 坐标量化。动态库缺符号或路径不支持时回退原 OpenCV。算法顺序仍是解码、去朦胧、镜头校正、基础/理光，预览与导出保持一致。

五张全分辨率 RAW/DNG 对比 C++ 与原 OpenCV，最大 RGB16 差异均为 1 个码值；镜头校正耗时从 1.15–1.65 秒降到 0.49–0.89 秒。测试覆盖太阳、烟花、建筑和风机样片，不能代替 Windows 或发行包验证。

## 相机配置的分阶段缓存（2026-10-10）

相机配置接入后，曝光在 RGB8 量化之前应用。仅保留最终显示底图会使每次曝光变化重新执行去朦胧、镜头校正以及相机空间 RAW 解码。当前增加校正后的相机 RGB16 / 参考 RGB16 源图层，以及曝光之前的增强相机 RGB16 层。手动曝光不进入后者的缓存键，去朦胧、自动曝光、非局部模式、算法版本、配置指纹和渲染后端仍参与键值。改变曝光只重算配置显示和后续调整，保持原曝光与高光裁切顺序。

## DNG 内嵌 WarpRectilinear：GPU 预览与导出（2026-10-10）

本节更新前一节的“WarpRectilinear 尚未应用”：现在优先使用源 DNG 的受支持 OpcodeList3，按原顺序执行 GainMap 和 WarpRectilinear，不再同时叠加 Lensfun 几何校正。三通道分别支持径向／切向参数，处理畸变和通道间几何差异。Metal 与 D3D12 默认尝试 GPU，使用独立 capability 查询，不依赖 Windows 相机配置 GPU 的 opt-in 开关；设备／算子不可用或 GPU 执行失败时回退 C++ CPU，旧库缺少 CPU ABI 时再回退 Python。实际后端写入导出任务的 `lens_correction.backend`。

`src/dng_warp.py` 有界读取 Classic TIFF、ActiveArea、方向、DefaultScale、DefaultCrop 和 opcode；支持单平面／三平面 Warp、一个兼容全帧 GainMap 以及方向 1/3/6/8。未知必需 opcode、未支持版本、多 Warp 或不兼容 GainMap 不会只应用一部分并声称成功。损坏／截断数据和非有限参数仍失败。无受支持内嵌路径时保留 Lensfun；缺少可靠校准仍按此前规则提示并继续未校正导出。
