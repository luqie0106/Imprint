# 滑杆预览的等待时间

Vue 的基础调整和去朦胧参数都走同一套预览调度。拖动时立即开始 L2 快预览，后续输入合并最新参数；请求开始之间至少相隔 16 毫秒。上一请求结束时若已超过该间隔，立即处理最新值，不再额外等待 45 毫秒。松手后立即用最终参数请求 L2，再在 100 毫秒空闲后升级全分辨率。升级等待本代最终 L2 完成，避免迟到的低分辨率结果覆盖全分辨率。首次选图立即启动快预览。Swift 原生编辑器同样首帧立即入队、后续以 16 毫秒合并输入；一次拖动只在开始时更新请求代次，使在途 L2 能持续显示。Swift 的空闲升级仍为 100 毫秒。刷新期间保留当前可见图片。

仅效果图模式不再先请求原图。切换到原图或对比模式时按需加载对应原图；已有的原图不会因基础参数变化而重复解码。

## GPU 逐像素矩阵与统一内存（2026-10-11）

增强转移的大数组运算新增 Metal compute：亮度比例、色差残差乘 3×3 矩阵、相机 RGB 合成和 RGB16 量化在一个 GPU kernel 完成；小型采样拟合仍在 CPU。auto/native 模式下，macOS 的 >=100 万像素图默认尝试 GPU，小图保持原 C++ 路径，因为 600×400 复制在内的热执行约 C++ 1.083 / Metal 1.108 ms，没有明显收益。显式 CPU 选择始终保留 CPU；`IMPRINT_NATIVE_CAMERA_PROFILE_TRANSFER=0` 关闭新算子，`1` 允许小图实验。旧 ABI、不可用设备或 GPU 故障继续回退 C++ / NumPy。Windows 不会为了这一尚未实现的算子反复创建 D3D12 renderer，现有 Windows GPU 算子保持原路由。

camera/reference 的只读对象复用上传，mutable 输入每次上传；处理与输出共享缓冲按尺寸复用，命令完成后才返回数组。仅去朦胧参数变化不再销毁配置 renderer；源变化、换图、超限淘汰、会话清理、空闲到期和退出仍释放 GPU 资源。2450 万像素时新增 transfer renderer 的两张源、处理和输出缓冲约 561 MiB，单独计入 GPU 资源，不属于前文 NumPy/JPEG 缓存预算。

直接截取真实 LCR_1132 预览中经过镜头校正的 camera/reference/增强 RGB16，交错执行 5 轮 C++ 和 Metal 完整转移函数（包括校验、采样拟合、复制、命令等待与回读），中位数为 **57.29→40.48 ms**，5 轮 RGB16 逐像素相同。独立预览接口 12 次请求的 JPEG 编码前 RGB8 哈希全部与改动前一致；LCR_1132 的首次和强度变化实际诊断为 `transfer_backend=metal`。单轮新 GPU 完整强度接口约 2.07–2.60 秒，仍受镜头校正、内存与系统调度波动影响，不能把矩阵算子的收益等同于整条链的提速比例。

真实矩阵对照脚本/结果：`/private/tmp/imprint-real-transfer-bench.py`、`/private/tmp/imprint-real-transfer-results.json`。完整 GPU 接口结果：`/private/tmp/imprint-memory-parallel-acceptance/after-gpu.json`。

此前 Mac 的 shared buffer 可由 CPU/GPU访问，但 NumPy 接口仍有 memcpy。依据 [Apple bytesNoCopy 契约](https://developer.apple.com/documentation/metal/mtldevice/makebuffer%28bytesnocopy%3Alength%3Aoptions%3Adeallocator%3A%29?language=objc)，无复制包装要求页对齐指针、页对齐长度和单一 VM region，并保证底层内存寿命。临时实验使用独立 mmap region 并在 GPU 完成、buffer 释放后才 munmap；同一全尺寸 kernel、相同一次 memcpy，生产式 `newBufferWithLength` + memcpy 为 82.81 ms，mmap + memcpy + bytesNoCopy 为 84.69 ms，输出完全一致。单纯换包装没有收益，该包装实验没有省去 memcpy；下面的直接写入实现才改变数据的落点。Windows 离散显存需要上传与回读，后续应缓存静态源并把相邻算子串在 GPU 内以减少往返；本机尚未做 Windows 硬件测试。

Apple 官方提供直接写入共享存储的方法：[Performing calculations on a GPU](https://developer.apple.com/documentation/metal/performing-calculations-on-a-gpu) 示例用 `newBufferWithLength:options:MTLResourceStorageModeShared` 创建缓冲，再取得 `buffer.contents`，让 CPU 直接生成输入数据；完成 GPU 命令后同样经 contents 读取结果。[contents()](https://developer.apple.com/documentation/metal/mtlbuffer/contents%28%29) 返回缓冲存储的系统地址，[shared](https://developer.apple.com/documentation/metal/mtlstoragemode/shared) 明确 CPU/GPU 共享访问系统内存，同时要求协调读写时机。因此本项目可让已有 C++ 转换 ABI 的 destination 直接指向 shared buffer.contents，GPU 输出也可通过保留 MTLBuffer owner 的 NumPy view 访问，省去格式转换后的一次输入 memcpy 和结果回读 memcpy。此方案已接入本地开发代码；rawpy 的解码仍自行分配，不能据此声称 RAW 解码全程零复制。共享输出被 NumPy/缓存引用期间不可销毁或复用，CPU/GPU也不可同时改写；连续滑杆可按 [Apple 多缓冲同步示例](https://developer.apple.com/documentation/metal/synchronizing-cpu-and-gpu-work) 使用缓冲池和完成通知，避免每帧全局等待。

新增 shader 与既有 GPU 算子的原生 CTest 为 2/2 通过；新增 GPU transfer 桥接与配置定向测试为 33 passed，覆盖大图默认、小图阈值、CPU选择、环境开关、旧 ABI 回退、只读源复用、可变源重新上传和失败清理。没有新增依赖或 Python 模块；PyInstaller 已包含 native_dense / camera_profile / native_renderer，跨平台构建仍编译现有 native target。Swift 未继续调整，没有提交、发布或启动替换用户当前应用；开发版需重启 Sidecar 才加载新库。

## C++ 镜头校正

镜头畸变和色差不能用单一 3×3 矩阵表达。现在缓存 Lensfun 已初始化的镜头参数计划，最多 4 项；焦距、光圈、距离、尺寸或校准文件变化会生成新计划。坐标按 128 行生成，用 C++ CPU 从连续 RGB16 数组重采样，避免原来的每条带、每通道整图复制。完整坐标图不常驻内存。暗角仍由 Lensfun 的原生绑定处理。

保持双线性插值和 reflect101 边界，并检测本机 OpenCV 的 float-map 插值路径；优化库可能使用连续坐标，普通路径使用 1/32 坐标量化。动态库缺符号或路径不支持时回退原 OpenCV。算法顺序仍是解码、去朦胧、镜头校正、基础/理光，预览与导出保持一致。

五张全分辨率 RAW/DNG 对比 C++ 与原 OpenCV，最大 RGB16 差异均为 1 个码值；镜头校正耗时从 1.15–1.65 秒降到 0.49–0.89 秒。测试覆盖太阳、烟花、建筑和风机样片，不能代替 Windows 或发行包验证。

## 相机配置的分阶段缓存（2026-10-10）

相机配置接入后，曝光在 RGB8 量化之前应用。仅保留最终显示底图会使每次曝光变化重新执行去朦胧、镜头校正以及相机空间 RAW 解码。当前增加校正后的相机 RGB16 / 参考 RGB16 源图层，以及曝光之前的增强相机 RGB16 层。手动曝光不进入后者的缓存键，去朦胧、自动曝光、非局部模式、算法版本、配置指纹和渲染后端仍参与键值。改变曝光只重算配置显示和后续调整，保持原曝光与高光裁切顺序。

新增独立共享缓冲 owner 与 C ABI；CPU 的 C++ RGB16 量化直接写入 `MTLBuffer.contents`，Lensfun 入口保留已有 uint16 存储，避免通用转换函数的冗余复制；校正输出保持共享存储，native 几何 remap 直接写入目标条带。相机空间矩阵的 GPU RGB16 输出直接作为显示配置的共享输入，显示配置 GPU RGB8 输出由 NumPy 视图持有。GPU 命令完成后才返回；每个输出独立分配，旧数组引用仍在时不会销毁或复用。清除 renderer/allocator 缓存后，旧视图的像素哈希仍保持一致。

Mac 默认对至少 100 万像素的 RGB 图启用；`IMPRINT_NATIVE_SHARED_MEMORY=0` 可回到复制路径，`=1` 可用于小图实验。CPU、Windows 和旧动态库继续走已有路径。RAW 解码、静态 camera/reference 首次上传、Lensfun 稳定源副本、去朦胧 float 输出、基础调整及 JPEG 编码仍有各自分配/复制，不是全流水线零复制。新模块已加入 PyInstaller datas/hiddenimports，没有新增依赖。

使用实图 `LCR_1132.NEF` 的校正后数据，6064×4040，同一矩阵和显示配置，8 轮按顺序交替关闭/开启共享；去掉首轮，剩余 7 轮中位数如下。计时包含新输出分配、量化、GPU 同步和 Python 接口，不包含 RAW 解码、镜头校正、基础调整或 JPEG 编码。

|阶段|复制路径|共享写入|
|---|---:|---:|
|C++ 量化及输出分配|47.01 ms|49.01 ms|
|GPU 相机空间矩阵|17.56 ms|15.83 ms|
|GPU 显示配置|37.19 ms|20.64 ms|
