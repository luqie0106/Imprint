# 滑杆预览的等待时间

Vue 的基础调整和去朦胧参数都走同一套预览调度。拖动时立即开始 L2 快预览，后续输入合并最新参数，上一请求结束后等待 45 毫秒再启动下一次更新；松手后立即用最终参数请求 L2，再在 500 毫秒空闲后升级全分辨率。升级等待本代最终 L2 完成，避免迟到的低分辨率结果覆盖全分辨率。刷新期间保留当前可见图片。

仅效果图模式不再先请求原图。切换到原图或对比模式时按需加载对应原图；已有的原图不会因基础参数变化而重复解码。

## 为什么去朦胧算子不到一秒，预览仍要数秒

之前的算子验收从已解码的线性 RGB 数组开始，测到约 0.65–0.90 秒。全分辨率接口还包括 RAW 解码、镜头校正、基础/理光调整和 JPEG 编码；前端此前还串行请求了原图。因此算子时间不能当作从松手到显示完成的时间。

2026-10-07 用 `LCR_9472.NEF`（6064×4040）、去朦胧强度 0.85、自动模式、Python 基础调整路径实测旧完整接口：

| 阶段 | 时间 |
| --- | --- |
| 额外的原图请求 | 1.31 秒 |
| 效果图 RAW 解码 | 1.07 秒 |
| 去朦胧 | 0.78 秒 |
| 镜头校正 | 1.55 秒 |
| 基础调整 | 1.45 秒 |
| 其余转换与 JPEG 编码 | 约 0.55 秒 |
| 效果图接口合计 | 5.40 秒 |

这些数值不包含前端定时器、旧请求排队、HTTP 传输和浏览器图片解码，也不是用户当前运行实例的计时。

## 内存缓存与回收

图像缓存只放进程内存，没有磁盘图片缓存。全分辨率只保留当前一张照片的两层：

| 缓存 | 上限 | 复用范围 |
| --- | --- | --- |
| 只读解码图与元数据 | 256 MiB | 原图、去朦胧参数变化和效果预览 |
| 去朦胧与镜头校正后的只读 RGB8 底图 | 96 MiB | 基础滑杆和理光参数变化 |

换到另一张全分辨率照片或源文件变化时，先释放旧两层再解码；会话淘汰时清理对应图。60 秒没有全分辨率请求后释放两层；后端退出取消回收计时器并清空。计时器是 daemon，不捕获图像数组。超过容量的图仍能渲染，但不留在缓存中。

去朦胧参数、算法版本、模式、自动曝光、色彩模式或后端变化只让处理后的底图失效，同张解码图仍可复用。基础参数变化重新执行后续调整及编码。导出独立读取全分辨率原图，不使用预览缓存。

低分辨率处理、显示、去朦胧数组缓存分别有 96、64、64 MiB 上限。去朦胧与理光 JPEG 缓存各限 16 MiB，同时保留 128 个条目上限。上述主要图像缓存合计最多 608 MiB，另有数量受限的缩略图、镜头计划和少量元数据；这不是整个进程的内存上限。解码、浮点处理、基础调整及编码会产生临时工作内存，需要另看进程峰值。

本机 2450 万像素照片的两层全分辨率缓存实际为 210 MiB。回收时先清空两层数组引用，再回收 Python 循环引用，并尝试 Darwin `malloc_zone_pressure_relief` / Linux `malloc_trim` 归还空闲页。符号缺失时安全跳过；Windows 尚未实测。该钩子只在空闲回收或关闭时执行。macOS 实图诊断进程峰值约 2322 MiB，触发空闲回收后 RSS 约 287 MiB；这不是 Tauri 整个应用的内存测量。

## C++ 镜头校正

镜头畸变和色差不能用单一 3×3 矩阵表达。现在缓存 Lensfun 已初始化的镜头参数计划，最多 4 项；焦距、光圈、距离、尺寸或校准文件变化会生成新计划。坐标按 128 行生成，用 C++ CPU 从连续 RGB16 数组重采样，避免原来的每条带、每通道整图复制。完整坐标图不常驻内存。暗角仍由 Lensfun 的原生绑定处理。

保持双线性插值和 reflect101 边界，并检测本机 OpenCV 的 float-map 插值路径；优化库可能使用连续坐标，普通路径使用 1/32 坐标量化。动态库缺符号或路径不支持时回退原 OpenCV。算法顺序仍是解码、去朦胧、镜头校正、基础/理光，预览与导出保持一致。

五张全分辨率 RAW/DNG 对比 C++ 与原 OpenCV，最大 RGB16 差异均为 1 个码值；镜头校正耗时从 1.15–1.65 秒降到 0.49–0.89 秒。测试覆盖太阳、烟花、建筑和风机样片，不能代替 Windows 或发行包验证。

## 完整接口实测

同一 `LCR_9472.NEF`，强度 0.85、自动模式、C++ CPU 去朦胧和 C++ CPU 基础调整，通过 HTTP TestClient 测得：

| 请求 | 完整接口时间 |
| --- | --- |
| 首次全分辨率效果图 | 3.18 秒 |
| 改基础曝光，复用处理底图 | 0.30 秒 |
| 改去朦胧强度，复用解码图 | 1.94 秒 |
| 原图，复用解码图 | 0.20 秒 |
| 首次 L2 | 0.55 秒 |
| L2 改基础曝光，复用分析底图 | 0.003 秒 |

上述全分辨率请求只解码一次。基础曝光变化产生新画面；命中底图与强制重建底图的同参数 JPEG 完全相同。基础八项（曝光、对比度、高光、阴影、白色、黑色、自然饱和度、饱和度）优先调用 C++ CPU；GPU 设置仍使用原 GPU 路径，不可用再回退 C++ CPU，旧库则回退 Python。基础调整从约 1.43–1.67 秒降到 0.15 秒，JPEG 编码仍约 0.11–0.14 秒。500 毫秒是升级调度延迟，不能宣称整个界面在 500 毫秒内完成。

全分辨率响应包含 `Server-Timing` 的 `wait/base/adjustments/encode/total`、`X-Preview-Base-Cache` 和 `X-Preview-Decode-Cache`。这些是本机接口计时，不包含前端计时器、传输或浏览器图片解码；尚未在用户当前 Tauri 实例测量。部署需要新动态库、新前端和重启 Python Sidecar。
